# Decisions (ADR log)

Short records of decisions taken while implementing `PLAN.md`. Newest last.

## ADR-001 — Target .NET 10 LTS, `net10.0-windows`, `.slnx`, central package management
- **Context:** Plan asks for the latest LTS .NET. .NET 10 (SDK 10.0.1xx) is installed and LTS.
- **Decision:** All projects target `net10.0-windows` (Core too, because NAudio WASAPI and DPAPI are Windows-only; Core still has no WPF reference). `CaptionOverlay.slnx` (the .NET 10 default solution format) instead of `.sln`. Package versions live in `Directory.Packages.props`.
- **Consequence:** `dotnet build CaptionOverlay.slnx`. Visual Studio 2022 17.13+ / Rider open `.slnx`.

## ADR-002 — Test stack: xUnit v3 on Microsoft.Testing.Platform, AwesomeAssertions
- **Context:** xUnit v3 + the .NET 10 SDK no longer supports the VSTest bridge for `dotnet test`. FluentAssertions 8 changed to a commercial license (Xceed).
- **Decision:** `global.json` opts into Microsoft.Testing.Platform (`"test": { "runner": ... }`); run tests with `dotnet test --project tests/CaptionOverlay.Core.Tests` or `--solution CaptionOverlay.slnx`. Use **AwesomeAssertions** (Apache-2.0 fork, same API as FluentAssertions 7) instead of FluentAssertions.

## ADR-003 — Ship a folder, not a single-file exe; size budget exceeded
- **Context:** Plan: verify single-file (`PublishSingleFile` + `IncludeNativeLibrariesForSelfExtract`), fall back to a folder if native loading is problematic.
- **Finding:** With single-file, Whisper.net's `NativeLibraryLoader` fails ("Native Library not found in default paths"): it looks for `runtimes\...\whisper.dll` next to the app, which is inside the bundle. ONNX Runtime was fine.
- **Decision:** Folder deploy (`scripts/package.ps1`): self-contained publish, zipped. Non-win-x64 native runtimes (Linux Vulkan ~56 MB, win-x86, win-arm64) are removed by a target in `CaptionOverlay.Core.csproj`.
- **Size:** 212.7 MB extracted / 84.6 MB zipped (v0.1.0). The plan's "< 150 MB" aim is **not met**: the self-contained .NET + WPF runtime is ~140 MB (WPF cannot be trimmed) and the Vulkan whisper runtime is 55 MB. The alternatives (framework-dependent, dropping Vulkan) contradict "user installs nothing" / "GPU with only the driver". Accepted.

## ADR-004 — GPU runtimes: CPU + Vulkan, no CUDA in v1
- **Decision:** Ship `Whisper.net.Runtime` (CPU) and `Whisper.net.Runtime.Vulkan`. Runtime order: CUDA → Vulkan → CPU → CPU-no-AVX (CUDA is only used if someone drops the CUDA runtime in; it is not shipped). "CPU only" setting restricts the order to CPU.
- **Why:** Vulkan covers NVIDIA, AMD and Intel with the normal driver (verified: RTX 4090, tiny model RTF 0.008 on Vulkan vs 0.022 on CPU). `Whisper.net.Runtime.Cuda` needs the CUDA runtime/cuBLAS DLLs, which are several hundred MB; per the plan it is deferred (possible optional add-on later). *The CUDA package size was not downloaded/measured in this session — re-check before revisiting.*
- **Note:** The native library is chosen once per process, so changing the GPU preference takes effect after an app restart (stated in the UI).

## ADR-005 — NAudio 3 API differences
- `WasapiLoopbackCapture` is obsolete in NAudio 3.1 → `new WasapiRecorderBuilder().WithDevice(d).WithLoopbackCapture().WithSharedMode().Build()`. Its `DataAvailable` delivers `ReadOnlySpan<byte>` plus `AudioClientBufferFlags` (silent packets are converted to zeros).
- Device notifications: `MMDeviceEnumerator.CreateNotificationClient()` returns an event-based `MMDeviceNotificationClient` (`DefaultDeviceChanged`, `DeviceStateChanged`, …) instead of implementing `IMMNotificationClient`.
- `WdlResampler.ResamplePrepare` returns the input buffer as `out Span<float>`.

## ADR-006 — Silero VAD version and location
- Bundled `silero_vad.onnx` from snakers4/silero-vad master (release v6.2.3 at download time, SHA-256 `1a153a22…88e3`, 2.3 MB). Its I/O is the v5 layout: inputs `input` [1, 576], `state` [2,1,128], `sr` (int64); outputs `output`, `stateN`. Like the reference implementation, each 512-sample frame is prefixed with the previous frame's last 64 samples.
- The model lives in `src/CaptionOverlay.Core/Assets` (not `App/Assets` as sketched in the plan) so the CLI and tests get it too.

## ADR-007 — Overlay positioning in physical pixels, bottom-anchored
- The overlay is positioned with `SetWindowPos` in physical pixels relative to the monitor work area and stored per monitor device name as fractions `{left, bottom, width}` (plan said "relative rect"). The window grows upwards with more text, so the bottom edge is the anchor. Missing monitor → primary monitor, bottom-centre.
- Height is computed from the content (`UpdateLayout()` then `Measure`), not with `SizeToContent`, to avoid WPF switching SizeToContent off when the window is resized from code.

## ADR-008 — Tray icon without Windows "efficiency mode"
- `H.NotifyIcon`'s `ForceCreate()` enables EcoQoS efficiency mode by default, which throttles the whole process. Real-time audio needs full scheduling, so it is created with `enablesEfficiencyMode: false`.

## ADR-009 — Hallucination filtering checks all languages
- The per-language phrase list (`Core/Captions/hallucinations.json`) is embedded; all languages are checked for every result because language detection is least reliable on the near-silent audio that produces these phrases. Long phrases (≥ 15 chars) match as substrings (e.g. "Untertitel im Auftrag des ZDF, 2021"), short ones only exactly.

## ADR-010 — Live timeline starts at session start
- WASAPI loopback delivers no packets while nothing plays. The session timeline (SRT timestamps) therefore starts when the pipeline starts, and silence is injected while no packets arrive (100 ms tolerance). Starting at the first packet shifted all timestamps by the initial silence (found in manual testing; regression test `LiveTimelineTests`).

## ADR-011 — Settings are sanitized on load
- Out-of-range or empty values (hand-edited / damaged files) are replaced with defaults when `settings.json` is loaded (`AppSettings.Sanitize`), so a bad file cannot yield an invisible overlay or a VAD that never fires.

## ADR-012 — A Whisper processor is built per inference
- The prompt (recent committed text) changes after every caption, and Whisper.net sets prompts at build time, so a processor is built per call from the single loaded `WhisperFactory`. Measured overhead is negligible compared to inference (tiny model: 12.8 s audio in ~100 ms on Vulkan including build).

## ADR-013 — Remote catalog source
- Remote catalog URL: `https://raw.githubusercontent.com/bergi9/whisper-live-caption/main/catalog/models.json` (4 s timeout). Used only if valid and `version` ≥ bundled; entries are validated (id/repo/file patterns, 64-hex SHA-256, no `.en` models, `https://huggingface.co` only). Until the repository is public/pushed the fetch returns 404 and the bundled catalog is used.

## ADR-014 — German test fixtures: commit 8 unchanged FLEURS clips, derive everything else in memory
- **Context:** `GERMAN_TEST_FIXTURES_PLAN.md`: German audio with known transcripts/timings for segmenter, SRT and WER tests. Source: FLEURS `de_de` via the Hugging Face dataset `FluidInference/fleurs-full`, pinned to revision `66b5a017…`, CC-BY-4.0.
- **Decision:** `captionoverlay-cli fixtures fetch-de` selects 8 clips deterministically and writes `tests/fixtures/de` (clips byte-for-byte unchanged, `clips/transcripts.json`, `manifest.json` with SHA-256, `ATTRIBUTION.md`). **Committed** (2.08 MiB of WAV), so CI runs offline. The composite, its 48 kHz stereo version, the reference SRT/cues and the 20 s silence are built in memory by `GermanComposite` (`src/CaptionOverlay.Cli/Fixtures`, linked into the test project, not part of Core).
- **Not downsampled:** the clips are already 16 kHz mono PCM16, Whisper's and Silero's native format. 8 kHz / 8-bit / lossy codecs would save ~1 MB but cut the 4–8 kHz band (s, f, sch, z), so WER would measure the damaged fixture. FLAC would need a new dependency. If the fixtures ever exceed 5 MB: gitignore the WAVs, keep manifest + transcripts, and let CI run `fixtures fetch-de` with a cache keyed on the manifest hash.
- **Selection details found while implementing:**
  - Transcripts are not fully clean: 11 lines end with a stray `.x`, 15 contain quotes. Clips with such transcripts are skipped (they would count as errors for every model). Hyphens are allowed; the WER normalization turns them into spaces.
  - The SHA-256 of every clip is in the tree API listing (`lfs.oid`); downloads are verified against it.
  - The plan's expected long clip `de_de_0000` has only 9.6 s of speech (not force-cut); `0007` and `0009` contain pauses ≥ `EndSilenceMs`. The first clip passing the VAD checks is `de_de_0011` (16.9 s). Normal: `0004 0005 0015 0016 0017 0019` (`0010` has the `.x` artefact). Short: `de_de_0739` (3.6 s).
  - VAD check: with force cuts disabled (`MaxUtteranceSec` = 600) a clip must be exactly one utterance; the long clip must also be force-cut with the default options. Speech spans come from the same run (clip padded with 1 s of silence, span = utterance ± pre-/post-roll).
  - Merge pair (0.3 s gap) = the two normal clips with the shortest speech, so the merged utterance stays below `MaxUtteranceSec` (`GermanComposite.Arrange` throws otherwise). Other normal clips fill slots 1–3 and 8 in id order.
- **Test adjustments vs the plan:** the backpressure variant of the SRT test uses a fixed 250 ms delay per job instead of "2× real time" (which would take > 2 min for the 69 s composite). The long clip is one cue in the reference SRT; the test expects it split into ≥ 2 lines. Tolerances as planned (±200 ms boundaries, ±50 ms 48 kHz vs 16 kHz, ±500 ms SRT starts).
- **WER baseline:** `tests/fixtures/de/wer-baseline.json`, refreshed by running the model tests with `CAPTIONOVERLAY_UPDATE_WER_BASELINE=1`. Measured on Vulkan; the CPU runtime gives slightly different text (e.g. base-q5_1 end-to-end 32 % on CPU vs 21 % on Vulkan), so the end-to-end limit (baseline + 5 points) is only asserted for models with a threshold.

## ADR-015 — Hallucination filter drops any text on inaudible audio
- **Finding:** `large-v3-turbo-german-q5_0` returns "Vielen Dank." for 10 s of digital silence. Adding it to the phrase list would also drop real "Vielen Dank." captions.
- **Decision:** `HallucinationFilter` drops any text when the utterance RMS is below `SilentRms` = 0.001 (≈ −60 dBFS; nothing audible, so any text is invented). In normal operation the VAD rarely lets such audio through, so this is a safety net; the fixed-window (no-VAD) path already skipped audio below the same level.

## ADR-016 — Custom-model validation must not pin the native runtime to CPU
- **Bug (found by the German model tests running after `Invalid_model_file_gives_clear_error`):** `LocalWhisperTranscriber.ValidateModelAsync` loaded with `GpuPreference.CpuOnly`, which also set the process-wide runtime order (chosen once per process). Importing a custom model before any model had loaded (e.g. in API mode) kept all later models on the CPU until restart.
- **Fix:** validation runs with `UseGpu = false` but configures the runtime order from the user's GPU preference (`ValidateModelAsync(path, settings.Engine.Gpu)`). Regression assertion in `Invalid_model_file_gives_clear_error`.

## ADR-017 — Dark mode via WPF Fluent; UI language via .resx with English fallback
- **Theme:** WPF's built-in Fluent theme (`PresentationFramework.Fluent`, part of the .NET 10 desktop runtime, no package). `App.xaml` merges `Fluent.xaml` (follows the Windows app mode); `ThemeService` sets `Application.ThemeMode` (System / Light / Dark, setting `general.theme`), which switches live. `ThemeMode` is still marked experimental (`WPF0001`, suppressed locally). Our brushes use Fluent keys (`ApplicationBackgroundBrush`, `TextFillColorSecondaryBrush`, `SystemFillColorCaution*`) instead of `SystemColors`, which stay light.
  - Implicit styles `BasedOn="{StaticResource {x:Type Button}}"` in `App.xaml` resolve to the classic Aero2 style, not Fluent's (check boxes rendered broken). App-wide implicit control styles were therefore removed; where a style must extend Fluent, base it on Fluent's named styles (e.g. `DefaultListBoxItemStyle`).
  - The caption overlay keeps its own colors (user-configured) and the edit toolbar keeps its dark look in both themes. Win32 `MessageBox` dialogs do not follow dark mode.
  - Visual change for light mode too: controls are now Fluent-styled (taller, rounded). Settings window 840×720, wizard 660×580.
- **Language:** `Loc` in Core (`CaptionOverlay.Core.Localization`): `ResourceManager` lookup over the app's `Strings.resx` and Core's `CoreStrings.resx`, English neutral resources as fallback for any missing translation, the key itself for unknown keys. Setting `general.uiLanguage`: `"system"` (default) follows the Windows display language, German if it is German, otherwise English; `"en"`/`"de"` pin it. The regional variant is kept for number formats (de-AT, en-GB).
  - One process-wide culture (`Loc.Culture`), not the thread culture, so messages built on background threads (downloads, API errors) match the UI. CLI and tests never set it and stay English (existing message assertions unchanged).
  - XAML uses `{l:Loc Key}` / `{l:Loc Key, Value={Binding X}}` (binding to an indexer, refreshed on `Loc.CultureChanged`), so switching the language in Settings updates open windows immediately. Combo box entries are `Choice` objects with label functions, re-translated in place so the selection is not disturbed; computed texts are re-read after the change.
  - Model notes come from `catalog/models.json` (English); German notes are keyed `ModelNote_<id>` in `Strings.de.resx` and fall back to the catalog text.
  - Logs, `HardwareSummary.ToString()` and the diagnostics export stay English. WPF's own texts (e.g. the text box context menu) stay English, because `SatelliteResourceLanguages=en` keeps the framework's German satellites out of the package; our own `de\*.resources.dll` are included.
  - `ResourceFileTests` check that every English key has a German translation with the same placeholders and that every key used in C#/XAML exists.

## ADR-018 — API models are picked from the provider's list, not typed
- **Problem:** a typed model id can be wrong, or valid but unusable: `gpt-realtime-whisper` exists but answers `404 Invalid URL (POST /v1/audio/transcriptions)`, because realtime models only work over OpenAI's Realtime (WebSocket) API.
- **Decision:** for OpenAI and Groq the API tab loads `GET {baseUrl}/models` with the saved key and offers only models that work with `/audio/transcriptions` (`OpenAiCompatibleTranscriber.IsTranscriptionModel`); picking one runs the connection test. A saved model missing from the list stays visible, marked "not usable for captions", instead of being switched silently. Without a key or connection the list holds the saved model and the provider default. The "Custom" provider keeps a text box (self-hosted servers often have no model list).
- **Filter, probed with a real OpenAI key (2026-09, English fixture through `/audio/transcriptions`):** works: `whisper-1`, `gpt-4o-transcribe`, `gpt-4o-mini-transcribe` (+ dated variants), `gpt-transcribe`. 404: `gpt-realtime-whisper`, `gpt-live-transcribe`. `gpt-4o-transcribe-diarize` rejects the prompt ("Prompt is not supported for diarization models"). Rule: id contains `whisper` or `transcribe` and not `realtime`, `live`, `diarize`, `tts`.
- **German quality (live tests, FLEURS clips; per clip / through the pipeline):** `whisper-1` 6.2 % / 7.8 %, `gpt-4o-mini-transcribe` 7.0 % / 7.0 %, `gpt-transcribe` 7.0 % / 6.2 %, `gpt-4o-transcribe` 4.7 % / 15.6–17.2 %: in the pipeline it dropped the second sentence of a two-sentence utterance. `whisper-1` stays the OpenAI default. Latency 0.5–2.4 s per utterance.
- Streaming models are now supported through the Realtime API (ADR-019) and listed as "(streaming)".

## ADR-019 — Streaming transcription over the Realtime API (gpt-realtime-whisper, gpt-live-transcribe)
- **Protocol, probed with a real key (2026-09):** `wss://api.openai.com/v1/realtime?intent=transcription`, `Authorization: Bearer` only (no beta header). One `session.update` with `session.type = "transcription"`, `audio.input.format = {audio/pcm, 24000}`, `transcription = {model, language}`, `turn_detection = null` (the default is server VAD). Audio: base64 PCM16 24 kHz mono in `input_audio_buffer.append`. Deltas (`conversation.item.input_audio_transcription.delta`) stream before the commit and carry the open item's id; `input_audio_buffer.commit` → `input_audio_buffer.committed {item_id}` (~0.13 s) → `…transcription.completed {item_id, transcript}` (~0.4 s). `input_audio_buffer.clear` → `input_audio_buffer.cleared`; the cleared item can still send a late delta, new audio gets a new item id. `expires_at` = connect + 60 min.
  - `gpt-realtime-whisper` rejects `prompt`, and a rejected `session.update` leaves the session on its defaults (server VAD, no model): so no prompt is sent and a session error is fatal. Both models accept `language` (`gpt-live-transcribe` turns it into `languages`).
  - A wrong key does not fail the handshake: the server accepts and then sends an `invalid_api_key` error event whose message echoes part of the key. Mapped to "API key rejected"; the message is not logged.
- **Design:** our VAD/segmenter keeps deciding where utterances start and end, so timestamps, SRT, the hallucination filter and the overlay work unchanged. `OpenAiRealtimeTranscriber` is an `ITranscriber`: partial passes upload only the samples not sent yet and return the live text; the final sends the rest, commits and waits for the transcript. `TranscriptionOptions` now carries the `UtteranceId` (to continue the same turn) and `ForcedCut`; discarded utterances reach the transcriber through `IStreamingTranscriber.CancelUtterance` (clear).
  - Streaming engines always run partial passes (they carry the upload; the live text costs nothing extra), every 250 ms, without the 1.5 s API throttle. The partials checkbox is hidden for them.
  - A final normally ends ~200 ms after the last speech while the partials already sent the whole end-of-sentence silence. That silence stays in the turn. The first version cleared and resent the utterance whenever the final was shorter than the streamed audio: every utterance was billed twice and the transcript came ~0.7 s later. Only a forced cut (`FinalUtterance.IsForcedCut`) restarts the turn, because then the streamed tail belongs to the next utterance.
- **Measured (live tests, RTX-independent):** English fixture at real-time speed, sentence end → final text 0.47–0.66 s (whisper-1 upload: 0.7–2.4 s), live words 0.1–0.3 s behind the audio. German composite through the pipeline: gpt-live-transcribe 8.6 % WER, gpt-realtime-whisper 12.5 % (it writes numbers as words, "fünfzehnten August neunzehnhundertvierzig", which the WER counts as errors). Price per the model page: gpt-realtime-whisper $0.017/min of audio sent (only speech segments are sent).
- **Known:** gpt-live-transcribe once returned an empty transcript for a whole clip appended in one burst (one-off test path); the app streams at real-time speed. Custom providers keep per-utterance upload; streaming is offered for OpenAI's streaming models.

## ADR-020 — Native Whisper model loads are serialized process-wide
- **Bug (found when the test suite started crashing with 0xC0000005 in parallel runs):** two `WhisperFactory.FromPath` calls at the same time (here: the tiny-model test and the German model tests) crash in `WhisperProcessorModelFileLoader.LoadNativeContext` — the ggml/Vulkan backend setup is not thread-safe. Serial runs passed; earlier parallel runs only passed by timing luck. The app can hit the same race (benchmark in the Models tab or the wizard while the engine loads or reloads a model).
- **Fix:** `LocalWhisperTranscriber` holds a process-wide gate around the native load (and around freeing a model). Inference itself is unchanged (per-instance). Verified with three consecutive parallel runs of the full suite.

## ADR-021 — Commit latency: no resend at forced cuts; animated caption lines
- **Measurement:** the pipeline logs, per line, how long after the utterance end it is committed (italic → normal), split into the segmenter's end-of-speech wait, queue and transcription. Compared on 90 s of recorded YouTube speech (continuous talk: 8 of 9 utterances end at the 12 s forced cut), played at real time through the CLI:
  - local large-v3-turbo-q5_0 (Vulkan): 1.2–2.4 s, of which transcription 0.35–0.5 s;
  - gpt-live-transcribe before the fix: 4.3–5.1 s, transcription 3.0–3.6 s. Cause: at every forced cut the streaming transcriber restarted the turn and resent the whole ~11 s utterance (the partials had already streamed audio beyond the cut point), so the server transcribed it again — and billed it twice.
- **Fix:** `PartialSnapshot.StableSamples` = the part a forced cut can no longer move to the next utterance (a cut only lands in the last `CutSearchMs` before `MaxUtteranceSec`). Streaming partials upload only that; the final sends the rest. After the fix: gpt-live-transcribe 1.1–2.6 s, transcription 0.7–1.2 s (≈ local + the ~0.5 s server round trip after the commit). Live text of long utterances pauses for their last ~2 s.
- **`delay` (gpt-live-transcribe) is not the knob:** commit → transcript stays ~0.5 s for every value; lower values only bring live words earlier and cost accuracy (German composite WER minimal 16.4 %, low 11.7 %, default 8.6 %). Kept at the server default; `ApiTranscriberOptions.StreamingDelay` exists for experiments.
- **Remaining (both engines):** with continuous speech the forced cut lands at the quietest point up to 2 s before the limit, so the line becomes final 0.85–1.9 s after its last word. Cutting earlier at short pauses once an utterance is long would shorten that (not done: it changes segmentation and the fixture expectations).
- **Animation:** overlay lines are one list (the tentative line becomes the committed line in place: italic → normal, opacity 0.72 → 1). `RevealDecorator` animates each line's height and opacity (350 ms, ease-out): new lines grow in at the bottom, old ones scroll out at the top, a line that wraps to another row grows smoothly. The window is sized for the end state (grows at once, shrinks after the animation) so it is not resized per frame (shrinking while visible flickered: changed in ADR-022). The first version rebuilt every line's outline geometry each frame (arrange at a moving offset) and ran at ~20 fps; the child is now arranged once and moved with a render transform, and `OutlinedTextBlock` reuses its geometry.
  - Animations were invisible at first because Windows "Animation effects" is off on the test machine and the decorator honoured it. It is now an overlay setting, "Animate line changes" (default on).
  - Developer switch `CAPTIONOVERLAY_DEBUG_AUDIO_FILE=<wav>` makes the app caption a WAV file in real time instead of system audio (repeatable overlay checks).

## ADR-022 — Overlay flicker: the window no longer shrinks while captions are visible
- **Measurement:** the app captioned 6 min of recorded YouTube speech (large-v3-turbo-q5_0) while every composed desktop frame over the overlay was captured (DXGI desktop duplication) and checked for A→B→A changes within 150 ms; a temporary trace logged line and window events on the same clock.
- **Cause:** 24 flickers, each 23–44 ms after the window shrank (220 → 174 px, one row less, whenever a two-row line scrolled out: 28 times, about every 11 s). Resizing a layered (per-pixel transparent) window shows its previous picture at the new position for one or two frames: the text jumped down by the height change with the bottom line cut off, then snapped back. Growing did not show it.
- **Fix:** while captions are visible the window only grows, with one text row to spare; it shrinks once the panel has faded out (invisible). In edit mode it still fits exactly. Same 6 min afterwards: 0 flickers, 5 resizes instead of 64 (the only shrink after the final fade-out). The extra height above the panel is transparent and click-through.
- Default overlay background opacity is now 70 % (was 55 %).

## ADR-023 — Local inference and other programs' frame rate (video stutter)
- **Measurement:** a WPF window rendering at the monitor rate (240 Hz) with enough GPU load to resemble video playback (full-window blur layers, ~24 % 3D engine) logged every frame interval while the CLI or the app captioned the 6 min recording with large-v3-turbo-q5_0 (Vulkan, RTX 4090). Counted: frames over 50 ms in 80 s.
  - Idle 0. Model only (CLI, no overlay): 332, worst 213 ms, the meter fell from 240 to ~55 fps: about five stalls per second of ~180 ms, one per inference pass (partials every 500 ms, plus finals). Finals only (no partials): 10 in 40 s.
  - `GGML_VK_PERF_LOGGER`: the encoder graph takes ~107 ms of GPU time because whisper always encodes a 30 s window; of that ~80 ms is plain attention (one f16 matmul alone 57 ms at 3.2 TFLOPS). Decoder steps take ~0.5 ms each. While the encoder runs, other programs' GPU work waits.
- **What did not help:** below-normal GPU scheduling priority (`D3DKMTSetProcessSchedulingPriorityClass`, call succeeds): 316 vs 332. `GGML_VK_ALLOW_GRAPHICS_QUEUE`, `GGML_VK_ASYNC_USE_TRANSFER_QUEUE`: no change. A shorter encoder window (`audio_ctx` = audio length + 1 s) cut the encoder to 23 ms but broke accuracy: German WER of large-v3-turbo 5.5 % → 39.8 % (repetition loops), tiny 37 % → 88 %; with a 10 s minimum 7.0 %, with 15 s 20.3 % (deterministic, repeated; not monotonic, so not safe). Rejected.
- **Decision:**
  - **Flash attention** on for GPU runs (`WhisperFactoryOptions.UseFlashAttention`): attention 80 ms → 2 ms, encoder ~44 ms; model-only stalls 332 → 176 frames over 50 ms, stalls ~100 ms instead of ~180 ms. Accuracy unchanged for the large models (turbo per clip 5.5 → 6.2 %, one word; end-to-end identical; German turbo identical), RTF 0.058 → 0.038. Base end-to-end 21 → 31 % (one line repeats a word; base is not recommended on a GPU).
  - **Background priority while a local model is loaded:** the process runs at below-normal CPU (and GPU) priority; the UI thread and the audio capture thread raise themselves back to a normal app's level. It helps where the CPU is the bottleneck (CPU runtime, busy machine); the GPU part had no measurable effect here. The CLI does the same (`--normal-priority` to compare).
  - **Overlay animations capped at 60 fps** (they ran at 240 Hz): with the light meter, hitches in 2 min went from ~190 (old) to ~100 (priority) to ~70 (priority + cap).
  - Whole app with everything: 183 frames over 50 ms in 80 s under the GPU load (before: 223). A partial interval of 1 s halves it (95): the setting "Partial update interval" is the remaining knob; partials off leaves one ~100 ms stall per line. API mode has no local GPU load.

## ADR-024 — Captions split into display rows; transcript files split by rule or on demand
- **Problem:** at the default 12 s longest sentence one caption line is two or three rows of text, too much to read at once; setting it to 5 s makes lines short but cuts sentences for Whisper.
- **Measured (German composite, end to end, longest sentence 12 / 8 / 5 s):** large-v3-turbo 8.6 / 6.2 / 7.8 %, large-v3-turbo-german 10.2 / 8.6 / 10.2 %, small 13.3 / 25.0 / 24.2 %, tiny 35.9 / 35.2 / 41.4 %; GPU work (RTF) 0.04 / 0.04 / 0.09 at 5 s (more passes, each encoding a 30 s window: more stutter, ADR-023). The composite is read sentences with pauses; continuous speech gets more mid-sentence cuts.
- **Decision (display):** the utterance length stays a recognition setting; the overlay splits each caption into rows that fit its width (`CaptionLineSplitter`): break after a sentence end if the row is at least half full, else after a comma/semicolon/colon/dash if 60 % full, else between words. "Lines shown" counts rows. Rows are keyed by utterance + row index, so tentative rows become committed in place and the existing grow/scroll animation moves row by row; a still-spoken utterance rolls up. Width comes from the window (text measured in the caption font, minus the outline, 3 % spare for italic). 150 s check with the frame capture: 0 flickers.
- **Decision (transcripts):** `TranscriptRecorder` owns the files. Rules (`TranscriptSettings.Split`): after a break without captions (default, 30 min; stopping and starting within it continues the file), each time listening starts (previous behaviour), or only manually. Tray "Split transcript now" starts a new file at once. Times in a file are relative to the file's start (the pipeline's session start + caption time), so an SRT spanning a stop and start stays continuous. Files are never overwritten (same-second names get `_2`). Restarting the app always starts a new file (no appending to old files).
- **Default longest sentence 8 s** (app setting; the engine/CLI default stays 12 s because the German fixtures are built around it): best end-to-end result for both large models above. The trade-off is explained in a tooltip on the setting (info glyph), not in the tab. Small is worse at 8 s than at 12 s on this set (13.3 → 25.0 %).
- **General vs German large-v3-turbo** (same 8 clips, per clip: 5.5 % vs 8.6 %): the gap is three words of spelling, not recognition. The German model wrote "Gallonen" correctly where the general one wrote "Galonen", but "Next Gen" (reference "nextgen") and "Ringerkollegen" (reference "ringer-kollegen", which the WER normalization turns into two words) count against it; both fail on the Indian names in clip 0019. With ~130 words the set cannot separate the two models; it only shows the German fine-tune is not worse in substance.

## ADR-025 — Speaches (self-hosted) as an API provider: per-utterance upload, not its Realtime API
- **Provider:** Speaches (faster-whisper server, OpenAI-compatible HTTP API). A preset with an editable server URL (default `http://localhost:8000/v1`), its own saved key (optional: a server without `API_KEY` needs none) and the model list from `GET /v1/models`. Speaches lists speech recognition and text-to-speech models together and adds a `task` field; models with a `task` are offered when it is `automatic-speech-recognition`, whatever their name (the OpenAI name filter of ADR-018 would drop e.g. Parakeet). The wizard shows a URL field for self-hosted providers (Speaches, Custom).
- **Why not its Realtime API (read in the source, v0.8.2 and master 2026-04):** it follows OpenAI's older beta protocol (`input_audio_transcription`, no `session.type`), resamples the 24 kHz input to 16 kHz by linear interpolation, and transcribes only the whole buffer at the commit through its own `/v1/audio/transcriptions`; no delta events. So there is no live text to gain, only a lossy resample and a WebSocket to keep alive. Probed on the test server (v0.8.2, key required): the WebSocket upgrade answers `500` with or without a key (plain HTTP answers `403` for a wrong key), so the endpoint is not usable there anyway. Partial captions stay the upload model's optional partial passes (free on an own server).
- **Rechecked with Speaches 0.9 (server rc build reporting "0.8.3" in its OpenAPI info, source v0.9.0-rc.3 and master 2026-04):** the WebSocket now checks the key (wrong key → `403` at the upgrade) and supports `?intent=transcription&language=…` with `model` as the transcription model. Still no transcription deltas anywhere in the source; the whole buffer is transcribed at the commit (no prompt, `response_format=text`) after a linear-interpolation resample from 24 kHz. Server VAD cannot be switched off: `session.update` accepts `turn_detection` only as an object (null is rejected), setting it always also sends an "unsupported `prefix_padding_ms`" error event, and its end-of-speech rule (last speech ending within a 3 s window) would cut our utterances. So the realtime path would give no live text and needs workarounds (VAD threshold 1.0, ignoring that error); per-utterance upload stays.
- **Measured (live tests against a Speaches v0.8.2 server, 2026-09):** `Systran/faster-whisper-small`: all 5 live tests pass; German clips 12.5 % WER, 1.3–1.9 s per clip; German composite through the pipeline 14.1 %. Real desktop audio (not in the repo): 6 min of an English video 1.8 % word difference to local large-v3-turbo-german, 150 s of a German reading 13.3 %, 1.4 s median per sentence, so it keeps up with live audio.
- **No OpenAI .NET SDK:** "OpenAI-compatible" is a promise about the HTTP API, which the hand-written client already speaks; Speaches' differences (`task`, no deltas) are server behaviour an SDK cannot hide. The client also carries app-specific handling the SDK would need wrapping for: fatal/transient/rate-limit mapping for the scheduler, one retry instead of the SDK's default three, the verbose_json → json fallback, and never surfacing error text that echoes the key (ADR-019). SDK 2.14 (~5 MB) now covers the GA Realtime protocol, so it stays an option if OpenAI's protocol changes again.
